# ADR 0010: Phase 6.1 — frontend design overhaul + bounded activity-context enrichment

## Status

Accepted. All five milestones shipped and verified: backend changes against the real
~1250-activity/4-year database via direct SQL and `pytest`/`ruff`/`mypy`; frontend changes via
`npm run typecheck && npx vitest run && npm run build` after every milestone plus
`javascript_tool` DOM/computed-style assertions against a real static build talking to a
host-run backend (this sandboxed environment cannot reliably screenshot the Browser pane — see
Consequences).

## Context

Phase 6 (ADR 0009) shipped real functionality — calendar grid, weekly/monthly rollups, Fitness &
Form, health dashboard — with **zero visual design**: the frontend had no CSS at all
(`frontend/src/**/*.css` didn't exist, `package.json` had no styling dependency), so every page
rendered as unstyled default-browser HTML. The user shared six Garmin Connect / intervals.icu
reference screenshots and wanted the app to go from "raw information" to something intuitive and
visually appealing, across four areas: calendar date navigation, the activity list, the activity
detail page, and a new combined "day view." A fifth area — bounded activity-comparison
enrichment (percentile rank, recent-activity context) — was added mid-phase once the design work
on the activity detail page made the gap concrete.

Two research passes grounded every decision below: an Explore-agent survey of the real database
inventorying which per-activity fields and streams actually have data (see decision 2), and
direct `sqlite3`/Python queries verifying specific claims (time-in-zone message shape, Body
Battery coverage window, `avg_running_cadence` scale, the percentile-rank algorithm) rather than
trusting FIT SDK docs or Garmin's displayed conventions from memory, per CLAUDE.md's standing
verify-don't-assume rule for vendor data.

## Decisions

### 1. Recharts adopted, reversing ADR 0008 decision 5's hand-rolled-SVG call

ADR 0008 chose a hand-rolled SVG polyline for the one stream-chart need that existed then: a
single already-downsampled channel, bounded point count, no zoom/pan/tooltip requirement. This
phase's reference images need synced multi-panel charts (one shared hover cursor across
elevation/pace/HR/cadence/power/temperature), a gradient-filled area series with an emphasized
endpoint marker (Fitness & Form), and a bubble-sized scatter plot (activity-context sparkline) —
three chart shapes ADR 0008's justification never covered. **Recharts** was picked as the one
new dependency: `syncId` gives synced multi-panel hover for free, `AreaChart`/`LineChart` cover
the Fitness & Form gradient, `ScatterChart` + `ZAxis` covers bubble sizing, all from one library
rather than accumulating several. Per CLAUDE.md's standing rule, its actual behavior (React 19
compatibility, real gzip bundle-size delta) was verified by installing and building it first,
before any other Milestone A work depended on it, not assumed from training data.
`StreamChart.tsx` was deleted outright once `ActivityCharts.tsx` (Milestone C) replaced its only
use; `FitnessChart.tsx` was migrated first (Milestone A) as a lower-risk proof the approach held
before committing to the much more complex multi-panel view.

Tooltip `formatter`/`labelFormatter` callbacks cannot declare explicit `number`-typed
parameters — Recharts' own generic types are wider (`ValueType | undefined`, `ReactNode`), so
every chart destructures/casts with `Number(value)` inside the callback body instead; this
matches a pre-existing pattern already in `RunningStats.tsx` rather than introducing a new one.

### 2. Real-data inventory gated scope before any UI was built

An explicit survey of `data/perseverer.db` before writing components split candidate features
into three buckets: buildable now (per-second stream channels already served by
`/activities/{id}/stream`; session-level `activity_metric` scalars like
`total_training_effect`/`workout_rpe`/running-dynamics averages; laps/splits; the existing
Fitness & Form and health dashboard data); not available at all — Garmin's proprietary GAP,
Performance Condition, and Stamina/Stamina Potential have zero rows anywhere and no raw field
exists, so no UI was built for them, consistent with CLAUDE.md's "never invent a plausible-
looking number" instinct; and raw-signal-exists-but-unmaterialized, which became real, scoped
backend work rather than either fabrication or silent omission (decision 3).

### 3. Time-in-zone materialized as its own FIT message type, not folded into the generic extractor

`fit/parser.py`'s generic per-row field extractor explicitly skips list-valued fields
(`isinstance(value, list): continue`), so `time_in_zone_mesgs` data was being parsed and
cataloged into `metric_definition` by name but never materialized as a value anywhere — a real
instance of the "raw first, never drop a field" principle being satisfied at the cataloging
layer but not the value layer. Verified by decoding archived FIT files directly rather than
trusting FIT SDK profile docs: `time_in_zone` is a dedicated message type (not a field on
`session_mesgs`), with one row per lap plus one row marked `reference_mesg: "session"` for the
whole activity. Only the session-level row is materialized, as
`fit.time_in_zone.time_in_hr_zone_<N>` / `..hr_zone_high_boundary_<N>` — zone count is read from
what's actually present in each file (7 time buckets for 6 configured boundaries in the sample
file checked), never assumed to be a fixed 5 or 6. A full `sync rebuild` (22,586 raw objects)
backfilled 1,230 eligible historical activities; this is a value-population fix over already-
archived raw bytes, not a change to what's archived, so it required no re-contact with Garmin
per CLAUDE.md's "raw first" guarantee.

### 4. Colour + icon system ("Direction B — Instrument Panel"): a hue always identifies a metric

Grew out of scope mid-Milestone-A once the first real pages under the new theme system revealed
the actual problem: `theme.css` defined eleven colours in both a dark and light theme, but only
`--color-accent` was ever used outside a chart SVG, and there were zero icons anywhere. Three
mockup directions were rendered as an HTML artifact against real 2025/2026 data and presented to
the user before any component code was written — quiet-signal rule-only tinting, an
instrument-panel tile treatment, and a gradient-hero banner. The user picked the instrument-panel
direction. The governing rule, enforced structurally rather than by convention: **a hue on
screen identifies a metric or a sport family; there is no decorative colour.**

Concretely:
- One hand-rolled stroke-icon sprite (`components/Icon.tsx`, `currentColor`-based) — no icon
  package dependency, the same one-considered-dependency posture that justified Recharts and
  nothing else.
- One data-driven style map (`metricStyle.ts`) assigning every sport and health metric a
  `{tone, icon}` pair, collapsing the real 14-sport catalog onto 5 tones (verified against the
  real catalog, not an assumed enum) rather than inventing 14 distinct colours.
- A `.tone-*` CSS utility where every tinted surface is a `color-mix()` off an existing
  `--color-*` token — no new hex value entered the codebase, and both themes keep working for
  free since the mix is relative to whichever theme is active.
- A shared `StatTile`/`MetricChip` presentation, replacing five files' worth of duplicated
  ad-hoc tile markup, with at most three "hero" (tinted, promoted) tiles per card by rule — not
  a per-page judgement call — so no single view can visually shout at the user more than any
  other.
- Charts were brought into the same system: `toneColor()` replaced picking chart-line colours by
  positional array index, which had let a metric render a different colour in a chart than on
  its own tile — a real, if minor, consistency bug this system closes structurally rather than
  by remembering to keep two colour choices in sync.

### 5. Milestone E: a bounded, self-excluding percentile-rank endpoint, not a Garmin-algorithm reproduction

`GET /activities/{id}/context` computes, as a direct query against `activity` (matching the
existing `/activities` list endpoint's precedent of a bounded lookup, not rollup-backed — this
is a decade-spanning-aggregate-shaped concern that a single-activity, single-request query
handles cheaply enough on the target hardware without one):

- **`percentile_rank`**: the share of this athlete's *other* same-sport activities within ±15%
  of this one's distance that it was faster than or equal to, by effective pace (moving duration
  preferred over elapsed via `coalesce(moving_duration_s, duration_s)` directly in the SQL, not
  computed Python-side). The activity being viewed is excluded from both the numerator and the
  denominator of its own percentile — not merely filtered from display — so a first-of-its-kind
  effort has no artificial "beat 100% of itself" result. `null`, never `0` or `100`, when
  `comparable_count == 0`, per the same "never invent a plausible-looking number" instinct that
  kept GAP/Performance Condition/Stamina out of this phase entirely. Verified two ways: a
  dedicated self-exclusion test, and an independent by-hand SQL/Python cross-check against the
  real archive that matched the endpoint's own output exactly (`comparable_count=10`,
  `percentile=20.0` on a real activity).
- **`recent`**: same-sport activities in the 90 days up to and including *this activity's own
  `local_date`* — deliberately not "today," so viewing a year-old activity shows its true
  contemporaries rather than a mostly-empty recent window. The current activity is deliberately
  *included* in this list (unlike the percentile pool) since it's meant to seed a sparkline
  showing where this effort sits among its neighbors, including itself.
- Frontend: `ActivityContextStrip.tsx` renders a plain-language percentile sentence plus a
  Recharts bubble scatter (bubble size = distance — the "bubble" half of a bubble/sparkline
  design, encoding a dimension the reference images' richer intervals.icu views also treat as
  visually distinct from pace/duration) with the current activity's point emphasized (full
  opacity, stroked) against the rest (faded to 0.35 opacity), y-axis reversed for pace sports so
  "faster" reads as "up," matching how speed's natural axis direction already reads. Renders as
  fully absent — no crash, no empty section — when there's nothing to show (fewer than two
  recent points and no percentile), confirmed against a real zero-distance strength-training
  activity.

This is a deliberately smaller, honest analog of the reference images' richer intervals.icu
comparison views, not a reproduction of their SPI metric or historical-trend charts, which rely
on intervals.icu's own proprietary model this project has no access to and would otherwise have
to fake.

### 6. Verification pattern: DOM/attribute assertions, not visual inspection

This sandboxed environment cannot reliably screenshot the Browser pane, so every milestone's
"manual verification" step concretely means `mcp__Claude_Browser__javascript_tool` assertions
against the live DOM of a real static build (`npm run build` + `npx serve`) talking to a
host-run backend: element/class counts, `getComputedStyle()` colours, bounding-rect positions,
SVG attribute values (`fill-opacity`, `stroke`, `--pie-deg`, etc.). Established in Milestone A's
colour/icon work and used unchanged through Milestone E. Podman's own port-forwarding on Windows
is separately known-flaky (see the podman-SQLite-WAL-corruption issue tracked outside this ADR)
and was not used as a verification path at any point in this phase.

## Consequences

- The "a hue always identifies a metric" rule is now a real constraint on every future frontend
  change, not just this phase's own components — a new page introducing an ad-hoc colour outside
  `metricStyle.ts`/`toneColor()` would be a regression of decision 4, not a style nitpick.
- `metricStyle.ts`'s sport→tone/icon map is real, verified data as of this phase, not a closed
  list — a new sport family showing up in future real data must be added there the same way the
  original 14 were categorized (checked against the real catalog), with the `neutral` fallback
  tone/icon staying "not yet categorized," never silently wrong.
- The percentile-rank algorithm in decision 5 is intentionally simple (distance-band + same-sport
  + pace comparison) and makes no claim to match any vendor's proprietary scoring — if a future
  phase wants a richer comparison model, it should be scoped and named as a new, separate
  feature rather than an extension of this endpoint's contract.
- Time-in-zone's fix (decision 3) closes one specific instance of the generic-extractor's
  list-valued-field gap; other list-valued FIT message types may have the same silent-value-drop
  characteristic and haven't all been individually audited — a future phase finding another one
  should follow the same message-type-specific materialization approach rather than trying to
  make the generic extractor list-aware, which risks the same "shape becomes anyone's guess"
  failure mode this phase's own per-message-type approach avoided.
- No podman/NAS deployment step changed in this phase — everything shipped and was verified
  against a host-run `uvicorn` + static frontend build. Updating the podman container's data
  volume and rebuilding the frontend image the way prior phases did remains a separate, explicit
  step before this phase's changes are considered deployed, not just implemented.
