Perseverer API

A REST/JSON API over a self-hosted archive of Garmin, Strava, and Eufy activity and health data. Every endpoint reads from precomputed rollups or content-addressed raw storage — nothing here scans years of history at request time.

This reference is generated from the live OpenAPI schema and cross-checked against the router source, so every field, default, and status code below reflects what the server actually does today.

Base URL https://your-perseverer-host/api/v1

Overview

The API is organized around eleven resources: Activities, Health, Sleep, Calendar, Fitness, Insights, Notes, Goals, Planned Workouts, Settings, and Auth. Every route is prefixed /api/v1. Requests and responses are JSON; request bodies on POST/PUT/PATCH must be sent with Content-Type: application/json.

There is exactly one athlete per deployment credential — every endpoint is implicitly scoped to the athlete resolved from your auth credential, so there is never an athlete_id parameter to pass yourself.

Base URL is deployment-specific. This API has no public multi-tenant host — you run it yourself (Docker/Podman), and the origin depends on how you've exposed it (a reverse-proxy hostname, a local port, a Tailscale address). Substitute your own origin for https://your-perseverer-host in every example on this page.

Authentication

Every route requires a credential except GET /healthz, GET /version, and POST /auth/login itself (login is the credential check). Present exactly one of the following:

1. Shared API key

Send X-API-Key set to the server's PERSEVERER_API_KEY environment variable. This is the simplest option for scripts, the MCP server, and single-athlete deployments — it resolves to the deployment's default athlete.

curl -H "X-API-Key: YOUR_API_KEY" \
  https://your-perseverer-host/api/v1/activities?limit=10

2. Per-athlete API key

Send X-API-Key set to a key minted for one specific athlete via sync athlete create-key (server-side CLI, printed once). The server compares its SHA-256 hash against athlete.api_key_hash and resolves to that athlete specifically. Same header, same request shape as above — the two key types are tried in order and are indistinguishable to the caller.

3. Session token (JWT)

Exchange a username/password for a short-lived bearer token via POST /auth/login, then send it as Authorization: Bearer <token>. This is what the web frontend uses. Tokens expire after PERSEVERER_JWT_EXPIRY_DAYS (default 30 days); there is no refresh endpoint — log in again once expired.

curl -X POST https://your-perseverer-host/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username": "jerome", "password": "YOUR_PASSWORD"}'

# => {"access_token": "eyJhbGciOi...", "expires_at": "2026-09-18T12:00:00Z"}

curl -H "Authorization: Bearer eyJhbGciOi..." \
  https://your-perseverer-host/api/v1/activities?limit=10

Failure modes

StatusWhen
401No credential presented (and the server has at least one auth method configured), or the credential presented is invalid, malformed, or expired.
503The server has neither PERSEVERER_API_KEY nor PERSEVERER_JWT_SECRET configured — auth fails closed, never open, so a misconfigured deployment refuses every request rather than silently accepting none. This is a deployment misconfiguration, not something a client can fix by changing its request.

Errors

Errors are returned as a JSON body with a detail field. Validation errors use FastAPI's standard shape and are the same across every endpoint, so they're documented once here rather than repeated per endpoint below.

422 · Validation error

Returned when a query parameter, path parameter, or request body fails type/shape validation before the handler even runs — e.g. a non-numeric limit, a malformed date, or a request body missing a required field.

{
  "detail": [
    {
      "loc": ["query", "limit"],
      "msg": "Input should be a valid integer",
      "type": "int_parsing",
      "input": "abc"
    }
  ]
}

loc is a path to the offending field (["query", name], ["path", name], or ["body", ...]); type is a stable machine-readable error code; ctx may add extra constraint details (e.g. {"ge": 1} for a range violation).

Conventions

Units

Every numeric value in every response is SI: metres, seconds, metres/second, kilograms, °C, watts, beats per minute. There is no unit-conversion query parameter — convert at display time in your own client, the same way this project's own frontend does.

Timestamps & dates

Two distinct date/time shapes appear throughout this API, and they are not interchangeable:

Field patternTypeMeaning
*_utcstring (date-time)An instant, always UTC, ISO-8601 (e.g. 2026-08-15T06:32:11Z).
local_datestring (date)A calendar date with no time component (YYYY-MM-DD), in whatever timezone the activity/observation actually happened in — not UTC-shifted. This is what the calendar UI groups and filters by.
utc_offset_sintegerSeconds east of UTC in effect at start_time_utc, for reconstructing local wall-clock time from the UTC instant.

start_date/end_date query parameters are always local_date-typed (YYYY-MM-DD) and both bounds are inclusive.

Pagination

The two endpoints that can return unbounded result sets (GET /activities, GET /health/observations) use the same envelope:

FieldType
itemsarrayThis page's results.
totalintegerTotal matching rows across all pages, not just this one.
limitintegerThe page size that was applied.
offsetintegerThe offset that was applied.

Every other list-returning endpoint (routes, map points, sleep sessions, insights, notes, fitness rollups…) returns a plain unbounded JSON array — these are all backed by precomputed rollups or otherwise-bounded queries, so pagination would add complexity without a real need.

"available: false" instead of a fabricated value

A handful of endpoints (activity weather, activity location, goal progress) describe data that may genuinely not exist yet — no GPS fix to geocode, no goal configured for a period. These return 200 with "available": false and every other field null, rather than a 404 or a guessed value. Always check available before reading the rest of the object.

Multi-value query parameters

Array-typed query parameters (metric_key, channels, metric_keys) are repeated, not comma-joined: ?metric_key=a&metric_key=b. (The one exception is ids on GET /activities/routes, which is a single comma-separated string — noted on that endpoint.)

Nullable fields

In every table below, a nullable tag means the field's type is a union with null and may legitimately be absent — most commonly because a source device never recorded that signal (e.g. avg_hr_bpm on a pool-swim activity with no HR strap), not because of an error.

Schema reference

Response object shapes referenced by name from the endpoints above. Every field is listed with its type; required means the field is always present in the response (it may still be null if also tagged nullable); optional means the field may be omitted from the JSON entirely.

MCP server

Every read endpoint above, plus create_note/list_notes, is also exposed as an MCP (Model Context Protocol) tool for AI agents, mounted at /mcp on the same host and gated by the same X-API-Key credential described in Authentication. Each tool is a thin wrapper that calls its REST counterpart in-process — the request/response shapes documented above apply there too. This page documents the REST surface; point an MCP-aware client (e.g. Claude Desktop, Claude Code) at https://your-perseverer-host/mcp to use the tool form instead.
